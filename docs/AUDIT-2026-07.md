## 摘要

项目的接口设计（`BaseDrive` / `DriveFile` / 驱动注册表）方向是对的，但**契约没有任何强制手段**：`BaseDrive` 不是 ABC，`@abstractmethod` 完全失效，没有一致性测试，没有 CI。结果是 22 个驱动各自漂移，其中若干处漂移已经变成静默的数据破坏。

三个最值得先处理的事实：

1. **5 个驱动永久不可用**，原因是注册表里的类名拼错，而 `try/except ImportError` 把拼写错误和"依赖没装"混为一谈，于是永远不会有人看到报错。
2. **`local` 驱动（唯一零依赖、README 和示例都在用的那个）三个基本操作全挂**。
3. **两处静默数据丢失**：pCloud 的 `delete()` 在路径拼错时会递归删空整个账号；ossutil 的 `rename()` 会把文件删掉然后返回成功。

### 1. 注册表类名拼错 → 5 个驱动永久不可用 **[已验证]**

`src/fundrive/drives/__init__.py` 导入的名字和子包实际导出的名字不一致：

| `__init__.py` 导入 | 子包实际导出 | 失效的 key |
|---|---|---|
| `OssDrive` (:58) | `OSSDrive` (`oss/__init__.py:2`) | `"oss"` |
| `WebDAVDrive` (:69) | `WebDavDrive` (`webdav/__init__.py:1`) | `"webdav"` |
| `LanzouDrive` (:84) | `LanZouDrive` (`lanzou/__init__.py:1`) | `"lanzou"` |
| `AliPanDrive` (:47) | `AlipanDrive` (`alipan/__init__.py:1`) | `"alipan"` |
| `AliPanOpenDrive` (:47) | `AliopenDrive` (`alipan/__init__.py:2`) | `"alipan_open"` |

每个 import 都包在 `except ImportError: X = None` 里（:9-118），第 155 行再把 `None` 过滤掉。所以**拼写错误和缺依赖产生完全相同的现象**——驱动静默消失，`get_drive("oss")` 抛 `不支持的驱动类型`。README 里这 5 个全标着 ✅✅✅✅🎉。

连带问题：
- `:186-189` 的 `ImportError` 分支**不可达**（`None` 已在 :155 被过滤），缺依赖时用户看到的是误导性的 `ValueError: 不支持的驱动类型`。
- `:188` 提示 `pip install fundrive[{drive_type}]`，但 `pcloud`/`mediafire`/`zenodo`/`tianchi`/`openxlab`/`s3`/`115`/`local` 在 `pyproject.toml` 里没有对应 extra（`pcloud` 还被拼成 `plcoud`，`pyproject.toml:39`）。
- `OSDrive` 在 `__all__` 里（:227）但不在 `AVAILABLE_DRIVES` 中——`"local"` 和 `"os"` 都指向 `LocalDrive`（:144-145）。

**修法**：删掉 `try/except`，改成显式的 `_OPTIONAL_DEPS` 映射 + 懒加载（见 P2.4）。让拼写错误在导入时就炸。

### 2. `local` / `os` 驱动的基本操作全部失效 **[已验证：实机运行]**

```
d = get_drive('local')
d.login()                                    -> NotImplementedError
d.mkdir("/", "newdir", return_if_exist=True) -> 返回 True，但目录根本没创建
d.download_dir("src", "out")                 -> AttributeError: 'dict' object has no attribute 'fid'
d.get_file_list("src")                       -> [{'path': 'src/g.txt'}]   # 没有 fid/name
```

根因，`src/fundrive/drives/os/drive.py`：
- `:15` `mkdir(self, path, exist_ok=True, ...)` 与基类 `mkdir(fid, name, return_if_exist)`（`core/base.py:206`）签名完全不同。调用方传 `return_if_exist=...` 时，`name` 被绑到 `exist_ok`，于是执行 `os.makedirs("/", exist_ok="newdir")`——**静默 no-op 并返回 True**。`core/test.py:128` 和 `os/example.py:90` 都是这么调的。
- `:76,:84` 返回 `List[Dict]` 而非 `List[DriveFile]`，且只有 `path` 键。`BaseDrive.download_dir`（`core/base.py:407`）访问 `file.fid` 立即 `AttributeError`。
- `:25` `shutil.copyfile(filepath, fid)` 把 `fid` 当**文件**路径，但 `BaseDrive.upload_dir:472` 传的是**目录** → `IsADirectoryError`。
- 缺 `login`/`delete`/`get_file_info`/`get_dir_info`/`rename`/`move`/`copy`/`get_quota`——全部可用 `os`/`shutil` 几行实现。
- `:24` 残留 `print(filepath, fid)`。
- `:93` `class LocalDrive(OSDrive): pass` 空壳。
- `fid` 是无沙箱的绝对路径，没有任何 root 限制；`os/example.py:36` 传 `root_path=` 会直接 `TypeError`（`__init__` 转发给 `object.__init__`）。

这是最该先修的驱动：零依赖、被文档和 `example/integration_examples.py:386` 引用、是所有人第一个试的。

### 3. pCloud：路径查不到时回落到根目录，然后递归删除 **[已验证：逐行确认]**

`src/fundrive/drives/pcloud/drive.py:104-114`，`_get_folder_id_by_path` 在**三种**情况下都返回 `self._root_fid`（即 `"0"`）：路径段没找到、API 调用失败、抛异常。

`delete()` (`:390-401`) 直接消费这个返回值：

```python
folder_id = self._get_folder_id_by_path(fid)      # 拼错 -> "0"
params = {"folderid": folder_id}
result = self._make_request("deletefolderrecursive", params)
```

即 **`drive.delete("/名字拼错了")` 会递归删除整个 pCloud 账号**。同一个陷阱还喂给 `mkdir`(:349)、`upload_file`(:657，传到根目录)、`rename`(:777)、`copy`(:852)、`share`(:1012)。

**修法**：`_get_folder_id_by_path` 找不到必须返回 `None` 或抛 `FileNotFoundError`，绝不能回落到根。所有调用点显式处理 `None`。这一条建议立刻改。

### 4. ossutil：`rename()` 删除文件却报告成功 **[已验证：逐行确认]**

`src/fundrive/drives/ossutil/drive.py:884-918`：

```python
parent_dir = os.path.dirname(fid.rstrip("/"))
new_path = os.path.join(parent_dir, new_name)   # :906 —— 只在日志里用到，never used
if self.copy(fid, parent_dir):                  # :908
    if self.delete(fid):                        # :910
        logger.success(f"重命名成功: {fid} -> {new_path}")
        return True
```

`copy(source, target)` (`:835-840`) 构造 `target = join(target_fid, basename(source_fid))`，即 `join(parent_dir, basename(fid))` = **`fid` 本身**。所以是自己拷给自己，然后把原文件删掉。`new_name` 从头到尾没参与过任何 OSS 操作。

结果：好情况下 ossutil 拒绝同源同目标、`copy` 返回 False、`rename` 永远失败；坏情况下自拷成功 → 文件被删 → 返回 `True` 并打印"重命名成功"。**两种情况都从未真正重命名过。**

### 5. Dropbox：4MB 整数倍的文件永远不会提交，却返回成功 **[已验证：逐行确认]**

`src/fundrive/drives/dropbox/drive.py:568-592`。分块循环里 `files_upload_session_finish` 只在 `len(chunk) < chunk_size` 分支调用。当 `file_size % (4*1024*1024) == 0` 时，最后一次 `f.read()` 返回 `b""` → `len(chunk) == 0` → `break` → **finish 从未调用**。会话被服务端丢弃，文件没创建，`:596` 返回 `True`。

### 6. MediaFire：`mkdir` 返回父目录 ID，后续文件写错位置 **[已验证：逐行确认]**

`src/fundrive/drives/mediafire/drive.py:309` `self.exist(fid, name)`，而 `exist(self, fid, *args, **kwargs)`（`:249`）把 `name` 吞进 `*args` 丢弃——**只检查了父目录是否存在**，几乎恒为 True。于是进入 :311-315，遍历 `get_dir_list` 找不到 `name`，最后 `return fid`（**父目录 ID**）。调用方拿着它 `upload_file(..., fid=父目录)`，文件写进上一层。

### 7. Amazon S3：`delete()` 对无尾斜杠的目录假报成功

`src/fundrive/drives/amazon/drive.py:277` 递归分支以 `fid.endswith("/")` 为条件。传 `"a/b"` 会走到 `:295` 对一个不存在的 key 调 `delete_object`——S3 返回 204，于是日志打 `✅ 对象删除成功` 返回 `True`，实际什么都没删。

### 8. 文叔叔：分块上传的异常被静默丢弃

`src/fundrive/drives/wenshushu/drive.py:892` `concurrent.futures.as_completed(future_list)` —— 返回值是**惰性生成器，从未被迭代**。因此每个分块的异常全部丢失，`upload()` 对一个残缺/损坏的上传返回 `True`。

### 9. `BaseDrive` 自身：关键字参数后接 `*args` → `TypeError` **[已验证]**

`core/base.py:411-418`、`423-431`、`476-483`：


语法合法，但 `*args` 是位置参数、会绑到已用关键字给过的前几个形参。`args` 非空时必然 `TypeError: got multiple values for argument 'fid'`。即**只要往 `download_dir`/`upload_dir` 传任何位置参数就崩**。同样的写法：`pan115/drive.py:160,237`、`baidu/drive.py:201`、`oss/drive.py:127`（splat 进 `oss2.Bucket` 的 `is_cname` 位）。

## P1 — 可靠性

### 11. 88 个 HTTP 调用里 81 个没有超时 **[已验证：grep 计数]**

完全无 `timeout` 的文件：`github`（11 处）、`gitee`（11 处）、`zenodo`（`_make_request:142`，即全部）、`pcloud`（`:193,684`）、`onedrive`（**全部 16 处**）、`wenshushu` 的 `Uploader`/`Downloader`（16 处，其中 `:710` 在 `while True` 轮询里）。`ossutil/drive.py:104` 的 `subprocess.run` 也没有 `timeout`。`oss/drive.py:89` 的 `connect_timeout=3600` 等于没有。

一个挂住的 TCP 连接会永久挂死调用方。`core/constants.py:21` 有 `DEFAULT_TIMEOUT = 30`，没人用。

### 12. 资源泄漏

- **22 个驱动没有一个实现 `close()` / `__enter__` / `__exit__`**。`requests.Session` 在 `__init__` 创建后永不关闭（`pcloud:38`、`zenodo:112`、`tsinghua:69`、`onedrive:69`、`mediafire:96`、`webdav:40`）。
- `wenshushu/drive.py:439,524`：**每次** `upload_file`/`download_file` 都新建一个 `_WSSBaseDrive`（新 Session + 一次匿名登录往返），从不关闭。而 `WSSDrive.login()` 建立的会话根本没被上传/下载用到。
- `dropbox/drive.py:470` `_, response = files_download(path)`，流式 `Response` 从不关闭；应改用 `files_download_to_file`。
- `openxlab/drive.py:334,512` 用 `stream=True` 只读 header，body 不消费、不 `close()`。批量下载时连接耗尽。
- tqdm 进度条无 `try/finally`：`oss:417,523`、`dropbox:459,533`——上传失败后进度条不关闭，污染终端。

### 13. `login()` 无条件返回 True

`openxlab/drive.py:113-121`、`tianchi:131-139`、`tsinghua:99-110` 的 200 / 非 200 / 异常**三个分支全部 `return True`**。另外 `pan115:77`、`baidu:58`、`alipan/drive_aligo:49`、`alipan/drive_open:59`、`webdav/drive4:28` 也是硬编码 `True`。只有 `webdav/drive.py:44` 真做了连通性探测。

配套问题：`core/base.py:176-188` 定义的 `_is_logged_in` / `_root_fid`，**只有 6 个驱动**（oss/ossutil/google/pcloud/dropbox/zenodo）设置。其余 16 个驱动 `drive.is_logged_in` 永远是 `False`。而 ossutil 有 17 处 `if not self._is_logged_in` 守卫，是别人都不遵守的约定。

### 14. `os.makedirs("")` 崩溃 —— 8 个驱动

各驱动的 else 分支把 `local_path` 设为裸文件名，`os.path.dirname` 得到 `""`，`os.makedirs("", exist_ok=True)` 抛 `FileNotFoundError`：`github:660`、`gitee:574`、`zenodo:993`、`openxlab:480`、`tianchi:458`、`tsinghua:420`、`ossutil:543`、`onedrive:526`、`mediafire:684`、`os/drive.py:70`、`webdav/drive4.py:124`。

**即"不指定保存目录、下载到当前目录"这个最常见用法，在 10 个驱动上恒定失败**，且异常还被外层 `except Exception` 吞成 `return False`。正确写法就在隔壁文件 `webdav/drive.py:145`（`if parent_dir:`），没有被复制过去。

### 15. 388 个 `except Exception` → 返回假值 **[已验证：grep 计数]**

全仓 388 处 `except Exception`（0 处裸 `except:`），绝大多数是 log + `return False/[]/None/""`。后果是调用方**无法区分"不存在"、"没权限"、"网络断"、"我们自己的 bug"**。

`core/exceptions.py` 定义了完整的类型化异常（`AuthenticationError`/`NetworkError`/`RateLimitError`/`FileNotFoundError`…），**只有 `github/drive.py` 用**，而且用得不一致（`login`/`upload_file` 抛，`exist`/`delete`/`download_file` 吞）。`OperationNotSupportedError`（`:115`）**没有任何一处抛出**——所有"不支持"的桩函数都是 log warning + 返回假值，和真失败无从区分。

### 27. oss 与 ossutil 是同一后端的两份实现，建议删掉 ossutil

同样的 AK/SK/bucket/endpoint 配置形状（`oss:106-117` vs `ossutil:135-146`，只差 secret store 的 `cate2` 命名，所以凭据得存两份），方法顺序、docstring、`type_mapping` 块、警告桩区块、`share` 返回结构全部对应。

ossutil 版严格更差：

| | oss（SDK） | ossutil（CLI） |
|---|---|---|
| 正确性 | 可用 | `rename` 毁数据（P0.4）；`get_dir_list` **恒为空**¹ |
| 延迟 | 进程内 HTTP，连接复用 | 每次调用 1-3 次进程启动 + 新 TLS |
| 解析 | 类型化 SDK 模型 | `split()` 人类可读 stdout，文件名带空格即错 |
| 进度条 | 有 | 无（`capture_output=True` 把 ossutil 自己的进度条吞了，而 `:24` docstring 声称"支持进度显示"） |
| 凭据 | 内存 | 明文落盘，默认权限 |
| 超时 | 有（默认值不好） | 无 |
| 额外依赖 | `oss2` | `funinstall` + 登录时下载二进制 |
| fid 命名空间 | `""` 为根 | `oss://bucket/` 为根 —— **两者不可互换** |

¹ `_parse_ls_output:207` 要求 `len(parts) >= 4`，而 ossutil 把目录（CommonPrefix）打印成单列，`len(parts) == 1` 被跳过。于是 `get_dir_list` 恒空，继承的 `upload_dir`/`download_dir` 永不递归。

唯一真实差异：`ossutil du` 能廉价拿 bucket 大小，而 `oss` 是 O(N) 扫描（`:851`）——一个 `bucket.get_bucket_stat()` 就解决了，不值 1037 行。

**建议**：删 `drives/ossutil/`，摘掉注册表 `:63-65,138,222`，把 `get_quota` 换成 `get_bucket_stat()`。若确实需要 CLI 逃生口，做成只 override `upload_file`/`download_file` 的 `OSSDrive` 子类。
